# Benchmark test changelog

The test definitions are versioned separately from the application and from the
model settings. Every run records `suiteVersion` and a SHA-256 `testHash` of the
prompts, checks and matrix entries. If those definitions change, the hash changes
and the baseline must be updated deliberately; a result delta is then visibly a
test change, not a model/settings regression.

| tuner v9 | 2026-11-07 | No item, check or prompt changes. The committed preset recipe keeps `repeatPenalty=1`, selects the shorter code system prompt, `temperature=0.4`, `min-p=0.1`, `top-p=0.85` and `contextSize=4096`: on the full 136-item code task it scores 58.8% against 55.9% for the defaults (paired b=4 c=13, exact p=0.049) with 51 output tokens against 108.5 and 1,090 ms against 1,760 ms at the same 148.1 MB host plus 1.425 GB VRAM; on the 48-item tuning rung it is 59.0% against 55.6% (p=0.2165) with 52 against 111.5 tokens. A controlled context A/B at equal 59.0% quality measured 1.573 GB total at 4,096 against 1.951 GB at 16,384, so 4,096 saves 378 MB (19.4%) with no quality loss; its latency order flipped between runs and is not claimed. The suite's largest code prompt is 687 tokens, so 4,096 is a benchmark-code choice, not a large-repository recommendation. The quality stage now treats context as a fit parameter: it keeps the smallest listed size that covers the selected tasks' prompt+answer budget (4,096 for code, 16,384 for recall) instead of the largest that fits. When adding or changing a prompt, check or matrix variant:

1. Bump `SUITE_VERSION` in `benchmarks/suite.mjs`.
2. Add a row to this table.
3. Run both phases with `--update-baseline` deliberately.
4. Do not claim a quality gain until the new baseline and test hash are committed.
